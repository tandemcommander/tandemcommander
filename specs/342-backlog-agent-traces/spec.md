# Feature Specification: Backlog loop traces in `.agent-traces/`

**Feature Branch**: `342-backlog-agent-traces`
**Created**: 2026-10-25
**Status**: Draft
**Input**: User description (Czech, summarised): "Look at the project
`E:\Projects\2026_hscr_ai_chatbot` (read only) and change the output of the
backlog traces the same way: into `./.agent-traces/`, and add that folder to
`.gitignore`. Change the format and structure of the output after the reference
project too. Then analyse the backlog system of that project and propose
changes and improvements we could take over. We do not have to take over
everything, only the improvements that benefit us."

## Context

The backlog loop (feature 247, `bin/backlog.sh start`, `tools/backlog/loop.py`)
writes one raw claude stream log per run into
`.git/tandem-backlog-loop/logs/<date>-<slug>.jsonl` (+ `.err`). It keeps only the
newest 100 and records nothing else about a run there. Today that folder holds
284 files (547 MB, 142 runs since 2026-10-20: 95 item runs, 47 auto-triages).

The reference project's backlog system (its feature 003, ADR 0004, contract
`specs/003-backlog-system/contracts/traces.md`) is a port of ours to TypeScript,
with a second harness (Codex). It keeps traces as **input for a future eval
system**: one folder per run in `.agent-traces/`, with the raw stream, the
stderr, metadata about the run, and a shared index. The loop never deletes them.

### Comparison with the reference: what is taken over and what is not

| # | Reference feature | Decision | Why |
|---|---|---|---|
| A1 | `.agent-traces/` per-run folders `<YYYYMMDD-HHMMSS>-<harness>-<slug>/` with `trace.jsonl`, `stderr.log`, `meta.json`; `index.jsonl`; attempt separator lines; ignored by git; never deleted by the loop; total size in `status` | **taken over** (User Stories 1–2) | asked for; the per-run metadata and the index let runs be compared and selected without reading 10 MB streams |
| A2 | `meta.json.commits` found by a `Backlog-Item: <slug>` trailer in each commit | **taken over in substance, not the trailer** | our run commits already carry the feature number as the subject prefix (`[NNN] …`), and the triage commits start with `backlog: auto-triage`. The commits are found by those, with no change to the skill's commit rules |
| A3 | Session lost before `system/init` → restart with the same session id (reason `restart`) | **not needed** | in our loop a run that never started never took its item's lock, so it already gets a fresh start after a backoff (contract 247, row "does not hold the lock, an error") |
| A4 | `No conversation found` recognised in the result's `errors` field, not only in stderr | **not needed** (measured during planning) | claude 2.1.310, resumed with an unknown session id, writes the text to **both** stderr and the result's `errors` (research R1). Our loop reads stderr, so it already stops at once on a lost session |
| A5 | Usage-limit reset time parsed from the result text (`You've hit your … limit · resets 5pm`) | **not taken over** | measured in our logs: the one real limit came with a `rate_limit_event` `status: rejected` and its `resetsAt`, which the loop already uses |

| A8 | `.cmd` twins of every `bin/` script, five `backlog-loop-*` scripts | **not taken over** | the maintainer works in Git Bash, and on 2026-10-24 we merged the five wrappers into one script; the loop gets `bin/backlog-loop.sh` (User Story 4) |
| A12 | `bin/backlog.sh` as the one entry to the backlog tool (`check`, `list`, `next`, …) | **taken over** (User Story 4, Clarifications) | today a person types `python tools/backlog/backlog.py …`; one short command in `bin/` with `--help` is easier to remember |
| A9 | Named read-only reviewer agent (`.claude/agents/backlog-reviewer.md`) | **not taken over** | our reviewer has to build, run saltests and GUI probes, and do negative controls, so a read-only agent cannot do it. The prompt already lives in one place (`tandem-backlog-implement` step 7) |
| A10 | Status answers within 2 s (SC-008 there) | **taken over as a criterion** (SC-004) | the traces are never deleted, so a status that sums their size must stay fast as they grow |
| A11 | Mutation test of the tool, fixture generated by the tool itself | **not taken over** | the reference itself deferred it. Our `test_backlog.py` / `test_loop.py` cover the rules and the processes |

## Clarifications

### Session 2026-10-25

- Q: Should the backlog and the loop be one script (`bin/backlog.sh` with a `loop` group) or two? → A: Two scripts. `bin/backlog.sh <command>` runs every command of the backlog tool (`check`, `list`, `next`, `new`, `set`, `move`, `lock …`, …). `bin/backlog-loop.sh start|pause|resume|stop|status` controls the loop (today's `bin/backlog.sh`, renamed). The two tools have commands of the same name (`start`, `status`), and the split keeps them apart without another level.
- Q: Should the skills and the loop call the backlog tool through `bin/backlog.sh` or keep `python tools/backlog/backlog.py`? → A: Through `bin/backlog.sh`. The skills' command alias and every command the skills, the loop's messages, the contracts and `CLAUDE.md` show use it. The Python file stays only as the implementation behind the script (the loop keeps importing it as a module).
- Q: What should `bin/backlog.sh` do with an old loop command typed from habit (`start --auto-triage`, `pause`, `resume`, `stop`, `status`)? → A: Nothing special. It is passed to the backlog tool like any other command and ends with the tool's ordinary usage error (exit 2). There is no redirect hint and no alias.
- Q: Should the loop really never delete traces, at about 100 MB a day? → A: Yes, never delete, as in the reference. `bin/backlog-loop.sh status` shows the total size, and cleaning up is the maintainer's decision. There is no size warning and no retention limit.

### Session 2026-10-25 (during implementation)

- The maintainer: "move the files and the structure from `.git/tandem-backlog-loop` into `.agent-traces/` and adjust them to the new naming and structure." → The old run logs are **moved**, not copied: each pair is copied, checked byte for byte, put in place under the new name, and only then deleted. The empty `logs/` folder goes too. The loop's control and state files (`loop.json`, `run.json`, `triage.json`, `pause`, `stop`, `imported.json`) stay in `.git/tandem-backlog-loop/`: they are state, not traces (FR-004, the reference keeps them in the git common dir too).
- Measured while implementing: `system/init` repeats at every turn of one claude process (after a wakeup or a task notification), so an old log does not show where an attempt started. Imported runs therefore record `attempts: []` and the index `attempts: null`. A run's commits are found from `HEAD` at its start (`base`), not from times: two runs in the same second saw each other's commits by time.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Every run leaves a complete, self-describing trace (Priority: P1)

The maintainer (later an eval system) opens `.agent-traces/` and finds one folder
per run of the loop: item runs and auto-triages. Each folder holds the run's
raw output with its attempts marked, its error output, and a `meta.json` that
says which item it was, the claude version and model, the session, when it
started and ended, how it ended (journal outcome, feature, branch, commits),
and every attempt with its ending. The folder is not tracked by git and does not
make the working tree dirty.

**Why this priority**: this is the requested change and the input for evals.
Today a log says nothing about its run without reading the whole stream and
`RUNS.md` side by side.

**Independent Test**: run the loop with the fake claude (`--claude-cmd`) over a
fixture repository through a closed item, a limit-then-continue item, and an
auto-triage. Check the folders, the files, the separators, `meta.json`, and that
`git status --porcelain` stays empty.

**Acceptance Scenarios**:

1. **Given** an eligible item, **When** the loop starts its run, **Then** a folder
   `.agent-traces/<YYYYMMDD-HHMMSS>-claude-<slug>/` exists before claude starts,
   with `meta.json` in phase `new` or `running`, and `trace.jsonl` that begins
   with an attempt separator line `{"type":"backlog_loop.attempt","attempt":1,"kind":"start",…}`.
2. **Given** a run interrupted by a usage limit, **When** the loop continues it,
   **Then** the same folder gets a second separator (`attempt 2`, `kind continue`,
   `reason usage-limit`), the output of both attempts stays in order in one
   `trace.jsonl`, and `stderr.log` has a header line for each attempt.
3. **Given** a run that ends with a journal row `closed` for feature NNN,
   **When** the loop concludes it, **Then** `meta.json` has phase `done`, outcome
   `closed`, feature `NNN`, the branch from the journal, the run's commits, and an
   `ended` time.
4. **Given** the auto-triage runs, **Then** its folder is named
   `<stamp>-claude-triage` and `meta.json` has kind `triage`.
5. **Given** traces exist, **Then** `git status --porcelain` is empty and the
   loop's clean-tree precheck passes.

---

### User Story 2 - The maintainer can find and size runs without reading streams (Priority: P1)

The maintainer reads `.agent-traces/index.jsonl` (one line per run that ended,
whatever the ending) to pick runs by item, outcome, feature or date. `bin/backlog-loop.sh status`
shows the current run's trace folder and the total size of all traces, because
the loop no longer deletes old ones.

**Why this priority**: without the index, choosing runs means opening every
`meta.json`. Without the size, never-deleted traces grow without anyone noticing
(about 100 MB a day at the current pace).

**Independent Test**: after the scenarios of Story 1, `index.jsonl` has one line
per ended run with the fields of the contract, and `status` (text and `--json`)
shows the trace folder and the total size.

**Acceptance Scenarios**:

1. **Given** a run ends (finished, refused, unrecorded, dropped by `--forget-run`,
   or stopped for a person in phase `failed` / `lost`), **Then** exactly one line
   is appended to `index.jsonl` with `dir`, `kind`, `slug`, `harness`, `model`,
   `started`, `ended`, `phase`, `outcome`, `feature`, `attempts`.
2. **Given** a run is interrupted and continued later (even after a restart of
   the loop or the PC), **Then** no index line is written until it ends, and then
   only one.
3. **Given** the loop runs an item, **When** the maintainer runs `status`,
   **Then** the line `trace: <folder> (traces total: <size>)` replaces the former
   `log:` line, and `--json` carries both values.
4. **Given** 150 runs, **Then** none of their folders is deleted by the loop.

---

### User Story 3 - The old logs join the new layout (Priority: P3)

The first `bin/backlog-loop.sh start` after this feature moves the existing
logs of `.git/tandem-backlog-loop/logs/` into `.agent-traces/` once, by itself,
so the eval input starts with the whole history, not only with runs after this
feature. Each old `<date>-<slug>.jsonl` / `.err`
pair becomes a run folder. Its `meta.json` is marked as imported and filled from
what can be known: the item or triage, the start from the name, the session and
model from the stream, and the outcome, feature and branch from the matching
`RUNS.md` row where one matches. The rest stays `null`, the attempts too (an old
log does not mark where an attempt started).

**Why this priority**: useful history (142 runs), but the new format works
without it.

**Independent Test**: a `start` over a fixture holding a few real old logs
creates their folders and index lines before anything else. A second `start`
imports nothing, also after the maintainer deleted some of the imported folders.
Each old pair is deleted only after its copy is in place and equal byte for byte;
the emptied old folder is removed.

**Acceptance Scenarios**:

1. **Given** old logs, **When** the loop starts for the first time after this feature, **Then** every pair has a run
   folder with the content byte for byte, `meta.json` (`imported: true`), and one
   index line.
2. **Given** the import ran, **When** the loop starts again (even after traces were deleted), **Then** nothing is imported again.
3. **Given** an old log of a run that is still pending (`run.json` names it),
   **Then** it is not imported as ended. The pending run continues in its new
   folder (Edge Cases).

---

### User Story 4 - Two commands in `bin/`: the backlog and its loop (Priority: P2)

The maintainer works with the backlog through `bin/backlog.sh <command>` (list,
next, check, new, …) and controls the loop through
`bin/backlog-loop.sh start|pause|resume|stop|status`. Each answers `--help` with
its commands. Nothing else in `bin/` is needed for the backlog.

**Why this priority**: it makes the backlog tool usable without remembering a
Python path. It also has to land together with the trace change, because the
loop's messages and `status` name these commands.

**Independent Test**: `bin/backlog.sh --help` lists the tool's commands;
`bin/backlog.sh list --section next` gives the same output as
`python tools/backlog/backlog.py list --section next`; `bin/backlog-loop.sh status`
gives what `bin/backlog.sh status` gave before; `tools/test_bin_help.py` passes for
both.

**Acceptance Scenarios**:

1. **Given** the repository, **When** the maintainer runs `bin/backlog.sh <command> [options]`
   for any command of the backlog tool, **Then** the output and the exit code are
   those of the tool.
2. **Given** a running loop, **When** the maintainer runs
   `bin/backlog-loop.sh pause` (or `resume`, `stop`, `status`, `start …`), **Then**
   it behaves as `bin/backlog.sh <the same>` did under feature 247.
3. **Given** `bin/backlog.sh --help` or `bin/backlog-loop.sh --help`, **Then** it
   prints what the script is for, its commands and examples, and exits 0.

### Edge Cases

- **An old loop command typed into `bin/backlog.sh`** (`start --auto-triage`,
  `pause`, `status`): the tool's usage error, exit 2, nothing changed (FR-017). A
  `start` with a slug and `--feature` is the tool's own command and works as
  before.

- **A pending run recorded before this feature** (`run.json` with a `log` in
  the old folder): the next start moves it into a new trace folder (earlier
  output kept as attempt 1 with unknown details) and continues it there. A run
  is never split across both layouts.
- **`.agent-traces/` missing or deleted by the maintainer while the loop waits**:
  it is created again at the next run. A deleted folder of the *running* run is
  recreated, and the write never crashes the loop. The loop says so, and the
  loss is the maintainer's choice.
- **Two runs starting in the same second** (an auto-triage straight after an item):
  the folder name gets a `-2`, `-3` suffix. No folder is ever reused.
- **`.gitignore` not yet containing `.agent-traces/`** (an old checkout): the
  clean-tree precheck would see the traces. The ignore line ships in the same
  change as the first write.
- **A slug longer than a comfortable path** (slugs reach 60+ characters): the
  folder name is the full slug. The repository root path plus about 100
  characters stays well within the limits Git Bash and Python handle on this
  machine.
- **`meta.json` while being rewritten**: it is replaced atomically, so a reader
  (status, an eval) sees the old or the new version, never half of one.
- **Disk full while writing the trace**: the loop treats it as it treats any
  failure to write its log today. Losing trace bytes never changes a verdict.
  The verdict comes from `RUNS.md` and the lock.
- **The claude version cannot be read** (`claude --version` fails):
  `harness_version` is `null`. The run is not refused for it.

## Requirements *(mandatory)*

### Functional Requirements

**Layout and ignore**

- **FR-001**: The loop MUST write every run's output under `.agent-traces/` at
  the repository root, one folder per run named
  `<YYYYMMDD-HHMMSS>-claude-<slug>` (an item run) or
  `<YYYYMMDD-HHMMSS>-claude-triage` (the auto-triage), with the local start time,
  and a `-N` suffix when the name exists.
- **FR-002**: `.gitignore` MUST list `.agent-traces/`. The traces MUST NOT affect
  `git status` or any precheck of the loop or the skills.
- **FR-003**: The loop MUST NOT delete traces (the retention of the newest 100 is
  dropped), and it MUST NOT warn about their size or limit it. Deleting them is the
  maintainer's decision; `status` shows the total size (FR-011).
- **FR-004**: The loop MUST NOT write run output to `.git/tandem-backlog-loop/logs/`
  any more. Its control and state files (`loop.json`, `run.json`, `pause`, `stop`)
  stay in the git common dir.

**Files of a run folder**

- **FR-005**: `trace.jsonl` MUST hold claude's stdout unchanged, appended live, so
  a crash keeps everything written so far. Before each attempt the loop MUST append
  one separator line `{"type":"backlog_loop.attempt","attempt":N,"kind":"start"|"continue","reason":R,"started":<ISO local with offset>,"harness":"claude","session_id":<uuid>}`.
  R is one of `-`, `usage-limit`, `error`, `stall`, `idle`, `killed`, `restart`
  (the last kept for format compatibility).
- **FR-006**: `stderr.log` MUST hold claude's stderr of all attempts, each preceded
  by a line `=== attempt N (<kind>, <reason>) <started> ===`.
- **FR-007**: `meta.json` MUST follow the reference format (`format_version` 1):
  `kind`, `slug`, `harness`, `harness_version`, `model`, `session_id`, `started`,
  `ended`, `phase`, `outcome`, `feature`, `branch`, `commits`, `why`, `attempts[]`
  (`attempt`, `kind`, `reason`, `started`, `ended`, `ending`, `error_kind`,
  `resets_at`, `exit_code`, `idle_killed`, `usage`), `counters` (`limits`,
  `errors`, `stalls`, `idles`, `restarts`), and `loop` (`pid`, `host`,
  `auto_triage`). It MUST be rewritten atomically at every phase change and at
  every attempt's end. Fields the loop does not know are `null`.
- **FR-008**: `outcome`, `feature` and `branch` MUST come from the run's journal
  row in `RUNS.md`. For a triage the outcome is `triaged`. A run that has not ended
  has `null`.
- **FR-009**: `commits` MUST list the short hashes, oldest first, of the commits
  the run made: on any branch, not reachable from `HEAD` at the run's start (an
  imported run, which recorded no such commit: between its start and its end).
  For an item, these are the commits
  whose subject begins with `[<feature>]` (when the journal row names a feature) or
  with `backlog: <slug>` (the subjects the skill uses for runs without a feature,
  for blocks and splits). For a triage, they are the commits whose subject begins
  with `backlog: auto-triage`.

**Index and status**

- **FR-010**: When a run ends in any way that drops or freezes its record
  (finished, refused, unrecorded, `--forget-run`, phase `failed` / `lost` at a stop
  for a person), the loop MUST append exactly one line to `.agent-traces/index.jsonl`
  with `dir`, `kind`, `slug`, `harness`, `model`, `started`, `ended`, `phase`,
  `outcome`, `feature`, `attempts`. A run continued after a restart MUST still get
  only one line.
- **FR-011**: `bin/backlog-loop.sh status` MUST show
  `trace: <run folder> (traces total: <size>)` in place of `log:`, and `--json`
  MUST carry the folder and the size in bytes. Every message of the loop that
  names a log today MUST name the trace folder.
- **FR-012**: The format of `meta.json` and of the index lines MUST match the
  reference contract field for field (English keys and values). A later change of
  the format MUST raise `format_version`.

**Loop robustness**

- **FR-013**: *(withdrawn during planning)* Recognising a lost session from the
  result's `errors` field is not needed: claude 2.1.310 also writes the text to
  stderr, which the loop already reads (research R1).

**Migration**

- **FR-014**: A run pending from before this feature MUST continue in a new trace
  folder that starts with its earlier output.
- **FR-015**: The first `start` after this feature MUST, before anything else,
  move the old logs into run folders (`imported: true`, fields reconstructed as in
  User Story 3, unknowns `null`) and append their index lines in start order. A
  pair is deleted only after its copy is verified byte for byte and in place under
  its final name; the emptied `logs/` folder is removed. It MUST record that the
  import is done in the loop's state folder, so it never runs twice, even after the
  maintainer deletes traces. The control and state files stay where they are.

**Commands in `bin/`**

- **FR-017**: `bin/backlog.sh <command> [options]` MUST run the backlog tool's
  command with the same arguments, output and exit code. `--help` (also `-h`,
  `help`, no command) MUST describe the script and list the tool's commands.
  It MUST NOT treat the former loop commands specially: `bin/backlog.sh pause`,
  `status`, or `start` without a slug end with the tool's usage error (exit 2) and
  change nothing.
- **FR-018**: `bin/backlog-loop.sh start|pause|resume|stop|status` MUST take over
  the whole behaviour, options, exit codes and help of today's loop script.
  Every text of the loop, the skills, the contracts and `CLAUDE.md` that names
  the loop's commands MUST name `bin/backlog-loop.sh`.
- **FR-019**: `bin/` MUST hold no other backlog scripts than these two.
- **FR-020**: The skills `/tandem-backlog` and `/tandem-backlog-implement` MUST run
  the backlog tool as `bin/backlog.sh …`. The loop's messages, the contracts of 242
  and 247 and `CLAUDE.md` MUST show the commands in that form.
  `python tools/backlog/backlog.py` is no longer a documented way to run the tool.

**Records**

- **FR-016**: The contract `specs/247-backlog-run-loop/contracts/loop-cli.md`
  (*Files*, *Status*) MUST be amended, with a new trace contract in this feature's
  `contracts/`. The 247 entry of `specs/FEATURE-HISTORY.md` and the 342 entry MUST
  say where the traces now are.

### Key Entities

- **Run folder**: one run of the loop (an item or a triage). Name = start time,
  harness, slug. Holds trace, stderr, metadata.
- **Attempt**: one claude process of a run (start or continuation). Marked by a
  separator in the trace and described in `meta.json.attempts`.
- **Run metadata (`meta.json`)**: the run's identity, environment, timeline,
  outcome and attempts. Rewritten as the run progresses.
- **Index line**: the summary of one ended run in `index.jsonl`, append-only.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For 100 % of the runs in the loop's tests (closed, blocked,
  limit-then-continue, error backoff, stall, idle kill, Ctrl+C then continue,
  refused, unrecorded, lost, triage), the run folder, separators, `meta.json` and
  exactly one index line (where the run ended) match the contract.
- **SC-002**: After any number of runs, `git status --porcelain` is empty, as far
  as traces go.
- **SC-003**: No trace is deleted by the loop. The test runs 101+ runs' worth of
  folders and finds all of them.
- **SC-004**: `bin/backlog-loop.sh status` answers in under 2 seconds with 1,000 run
  folders and 5 GB of traces.
- **SC-005**: *(withdrawn with FR-013)*
- **SC-006**: The import turns all 142 existing runs' logs into run folders,
  byte-identical in content. A second `start` imports nothing.
- **SC-007**: `python tools/backlog/test_loop.py` and `test_backlog.py` pass, and
  `tools/test_bin_help.py` passes, and it covers both `bin/backlog.sh` and
  `bin/backlog-loop.sh`.
- **SC-008**: After the change, the skills, contracts, loop messages and
  `CLAUDE.md` contain no instruction to run `python tools/backlog/backlog.py`
  and no loop command in the form `bin/backlog.sh start|pause|resume|stop|status`.
  A text search finds 0 of either outside the history records (`specs/FEATURE-HISTORY.md`,
  earlier features' folders).

## Assumptions

- "The same way as the reference" means the same layout, file names and JSON
  fields. The texts (stderr headers, messages) are in English like the rest of the
  tool.
- The harness name is always `claude`. It stays in names and fields only for
  format compatibility with the reference.
- Never deleting traces is confirmed (Clarifications). At about 100 MB a day, the
  maintainer cleans `.agent-traces/` by hand when the size in `status` says so. The
  loop gives no warning and has no limit.
- Manual (interactive) runs of `/tandem-backlog-implement` leave no trace. Only the
  loop writes traces, as in the reference.
- No product code, installer, `PRIVACY.md` or UI string changes. The traces are a
  local developer artefact of the repository, not of the program.
- The import of old logs is not a separate command. `start` does it once by
  itself (research R6), so `bin/backlog-loop.sh` keeps its five commands.
