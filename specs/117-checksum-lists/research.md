# Research: feature 117 - checksum lists in any encoding

Measured on this machine (Windows 11, ACP 1250, OEMCP 852) on 2026-10-05, without starting
Tandem Commander (day mode: the installed program was in use and shares the registry key with
every GUI probe). Scratch files under the session scratchpad; the fixtures and the offline model
are committed under `probe/`.

## A. What the tools write (measured)

| Writer | Encoding of the names | Mark | Line end | Other |
|---|---|---|---|---|

No measured tool writes UTF-32. DOS tools (OEM code page) exist but were not available.

## B. What the plug-in read before this feature (code reading + primitive measurements)

`CVerifyDialog::LoadFile` read the bytes as they are and treated them as UTF-8 (feature 004,
`specs/104-.../research.md` 2 recorded "list-file encoding" as open):

1. **Code-page list**: an accented name is not valid UTF-8 -> `SplU8ToWExtAlloc` fails -> the
   look-up is skipped -> "missing". (A byte sequence that happens to be valid UTF-8 names another
   file.)
2. **UTF-8 with a mark**: `LTrimStr` skips only bytes <= space, so the mark stays in the first
   line: its first word is `EF BB BF` + the checksum (35 / 43 / 67 bytes) -> not a checksum -> the
   whole list is refused ("not a checksum file") - also when the first line is a `;` comment (the
   mark hides the `;`). An SFV list: the first name gets the mark -> "missing".
3. **UTF-16**: the buffer is a C string, so it ends at the first NUL byte (byte 1 or 2) -> refused.
4. **`./name`, `dir/../name`, `a//b`** (find-based lists): the path is joined and opened in
   extended form (`\\?\C:\...`), which keeps `.` and `..` literally - measured with
   `FindFirstFileW`: `\\?\...\.\name` -> error 123, `\\?\...\sub\..\name` -> error 123 (the plain
   form finds the file). **Every such line was "missing" since feature 004.**
5. **Wildcards** - the existence check was `FindFirstFileW`, which matches patterns, also in
   extended form (measured): `???.txt` found `a b.txt`; `<.txt` found `a b.txt`; `voil?.txt` and
   `voil>.txt` found `voil<U+00E0>.txt`. The row then showed that other file's size, and the open
   (`CreateFileW`, no patterns) failed with an error box (Retry / Skip / Cancel). `GetFileAttributesExW`
   on the same names: error 123 (no match). `???.txt` is exactly what `Set-Content` writes for a
   Cyrillic name (A).
6. **A folder named in a list**: found -> "exists" -> the open fails -> error box.
7. **GNU escape** (`\<hash> *sub\\x.txt`): the first word is `\` + the checksum -> refused.
8. **Display**: `SetDispInfoText` converted strictly (`CP_UTF8`, `MB_ERR_INVALID_CHARS`) and fell
   back to the code page - a WTF-8 name (lone surrogate) was shown as code-page garbage.

## C. What other tools read of the plug-in's own lists (measured, Python replica of `SaveHashes`)

| Variant | coreutils 8.32 `sha256sum -c` | 7-Zip 22.01 `7z t -thash` |
|---|---|---|
| 0.1.x as written: CRLF + `;` header | **every file "FAILED open or read"** (the CR is part of the name), exit 1 | **"Cannot open the file as [Hash] archive"** |
| CRLF, no header | fails (CR) | OK |
| LF + `;` header | OK, 1 "improperly formatted" warning, exit 0 | refused (comment) |
| LF + `#` header | OK, no warning | refused (comment) |
| **LF, no header** | **OK, exit 0** | **Everything is Ok** |

Total Commander reads LF and UTF-8 without a mark (A). Tandem's own reader (every version)
splits on CR and LF and skips `;` / `#` lines. So the md5/sha* lists were unreadable by the two
most common other verifiers on Windows; the SFV list (`;` comments are the SFV convention, coreutils
and 7-Zip do not read SFV) is not affected.

## D. Code-page conversion facts (measured, `MultiByteToWideChar` with `MB_ERR_INVALID_CHARS`)

- Single-byte code pages 1250, 1251, 1252, 852: every byte converts, to exactly one character;
  undefined positions of 1250 (81, 83, 88, 90, 98) give the C1 control of the same number
  (U+0081 ...) - one character per byte, no look-alike (a code page -> UTF-16 conversion has no
  best fit; best fit is the other direction).
- Double-byte 932: a lead byte alone or with an invalid trail byte fails the whole call (error
  1113) - the decoder converts character by character after such a failure (saltests).
- OEM 852 `c-caron` (9F) read as 1250 is `z-acute`; `s-caron` (E7) is `c-cedilla`: an OEM list read
  as the code page names `z-acute e c-cedilla tina.txt` - another name, normally not a file.

## E. Decisions (the contract of `src/common/salcsumlist.h`)

1. **One encoding per file, never per line**: byte order mark (UTF-8, UTF-16 LE, UTF-16 BE) ->
   that; else NUL bytes concentrated on one parity (at least 1 in 16 bytes) -> UTF-16 without a
   mark (Total Commander reads those too; a text list never holds NUL); else the whole file is
   WTF-8 -> UTF-8; else the code page (`GetACP()`). Rejected: per-line fallback ("this line's
   UTF-8 name does not exist, try the code page") - it lets one list name two different files for
   one byte sequence and is the look-alike risk the 102/104 lesson forbids.
2. **OEM is never guessed**: nothing distinguishes an OEM list from a code-page list (both decode
   every byte); trying OEM when the code-page name is missing is the per-line fallback rejected
   above. An OEM list's accented names are reported missing (unless the code-page reading of the
   bytes happens to name an existing file - then that file is verified, and almost surely
   CORRUPT). Recorded limit.
3. **Exact conversion**: an undecodable byte (a marked UTF-8 file with a broken byte, a broken
   double-byte sequence, a cut-off UTF-16 unit, a NUL) becomes `SAL_CSL_BADCHAR` = 0xFF - never
   valid in UTF-8, not white space (so `LTrimStr` / word splitting do not eat it and the line keeps
   its checksum and its shape); a name holding it is reported missing, shown with U+FFFD.
4. **A mark at the start of any line is dropped** (concatenated lists); elsewhere U+FEFF stays.
5. **Names**: a name with a control character, 0xFF, or `* ? < > " |` is reported missing without
   a look-up; the look-up is `GetFileAttributesExW` (no patterns), a folder is not a file.
6. **Paths**: `/` is a separator; empty and `.` components dropped, `..` removes the previous one,
   never above the drive or the share (as Win32 normalisation did before 004); one leading
   separator stays relative (unchanged). An absolute name (`X:\...`, or any name starting with two
   separators - UNC, `\\?\`, `\\.\`) is used **only when its root is the list's own root** (the
   same drive, the same `\\server\share`, ordinal case-insensitive); otherwise it is missing without
   any file-system call (review B1: a UNC look-up connects to the server and sends the user's
   credentials). Before 117 every absolute name was missing (joined to the folder). Trailing dots
   and spaces are **not** stripped (another file - 102). A `:` other than a drive letter's makes a
   name unusable (streams, `C:name`).
7. **"The same file" is the file system's rule** (092): the path goes to the file system; case
   follows the volume (NTFS: case-insensitive); NFC and NFD spellings are different names
   (a list written on macOS with decomposed names reports them missing - correct).
8. **GNU escape**: a hash-first or tag line starting with `\` is unescaped (`\\`, `\n`, `\r`); SFV
   lines are not (a leading `\` there is a rooted name, kept as before).
9. **Writing**: md5/sha* lists LF, no comment line (the only variant both coreutils and 7-Zip
   read, C); still UTF-8 without a mark and two spaces; SFV unchanged (CRLF + `;` header). The
   plug-in's lists of 0.1.x stay readable (UTF-8).
10. **NUL bytes**: trailing ones are no part of the detection and, like those at a line's start
   or end, are ignored (0.1.8 read a list with a trailing NUL - its text ended there); a NUL inside
   a line is 0xFF (never a line end: a cut name is another file's). BOM-less UTF-16 needs one parity
   to dominate (other parity <= 1/8) and >= 1 NUL in 16 bytes.
11. **System code page UTF-8 (65001)**: a list that is not UTF-8 goes the code-page way, every
   non-UTF-8 byte becomes 0xFF - those names are missing.
